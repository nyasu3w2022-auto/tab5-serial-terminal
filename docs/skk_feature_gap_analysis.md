# TAB5 ローカルSKK：追加仕様と記号・句読点の調査

**作成者:** Manus AI

**対象:** `feature/local-japanese-ime` のローカルIME実装

**目的:** 一般的なSKKの操作体系と現行TAB5実装を照合し、シリアル端末として安全に追加すべき機能を優先度付きで提案する。

## 結論

現在の実装は、ローマ字かな変換、候補循環、送り仮名、促音開始の送り仮名、`q`によるかな種別の相互変換、`Ctrl+J`確定、未確定時の特殊キー整合、候補学習、手動ユーザー辞書、補助辞書、句読点設定、`z`記号入力、temporary ASCII入力まで到達している。

| 優先度 | 次の機能・課題 | 推奨理由 |
|:---:|:---|:---|
| P1 | 略語入力（`/`） | コマンド名、URL、パス、英単語を日本語モード中に扱いやすくする。 |
| P1 | temporary ASCII入力と`l`系小書きかなの整理 | `l`はASCII入力の開始に使うため、`la`、`ltu`等の別名入力と競合する。`x`系小書きかなを標準として明確化する。 |
| 完了 | **SDカード経由のユーザー辞書インポート／エクスポート** | 書換え可能なSPIFFS上の学習辞書をバックアップ・移行できる。インポートは置換ではなく、既存候補を保持するマージを既定とし、明示確認した場合だけ置換を許可する。 |
| P2 | 数値変換 | 漢数字、全角数字、日付候補の入力を改善する。 |
| P2 | 見出し語補完 | ユーザー辞書の登録語が増えた後、Tab補完により入力効率が上がる。 |

> **推奨:** SDカード経由のユーザー辞書インポート／エクスポートは実装済みである。次の実装単位は`/`略語入力とASCII入力仕様の整理とし、その後に数値変換・見出し語補完を検討する。

## 現行実装の確認結果

現行のIMEコアは小文字ローマ字を未確定かなとして保持し、Spaceで候補検索、Enterで確定する。候補表示中はSpace／Left／Rightで循環でき、Enterで候補をUTF-8として送信する。大文字による見出し語・送り仮名、`q`でのひらがな／カタカナ相互変換、促音で始まる送り仮名も扱う。

ただし、IMEの特殊キー処理対象はEnter、Backspace、Left、Right、Escapeに限られる。Tab、Delete、Up/Down、Home/End、Page、Insert、ファンクションキーはIME外へ流れる。このため、未確定文字列や候補を残したままリモートの補完・編集操作だけが実行される可能性がある。

| 項目 | 現在の挙動 | 評価 |
|:---|:---|:---|
| `.` | IME内で`。`へ変換 | 日本語文として有用。ただしリモートの`.`入力が必要な場面ではIME解除が必要。 |
| `,` | IME内で`、`へ変換 | 同上。句読点種別は固定。 |
| `-` | IME内で`ー`へ変換 | 長音符には有用。ただしハイフン、オプション、負数などを直接打つ用途と競合する。 |
| `!`、`?`、`:`、`;`、`/`、`@`、`#`、括弧等 | かなバッファへASCIIのまま追加される | UTF-8としては送信できるが、候補検索の読みへ混在する。日本語記号への変換方針も未定義。 |
| 数字 | かなバッファへASCIIのまま追加される | 数値変換、全角数字、日付形式は未対応。 |
| `q` | 未入力ならかなモード切替、未確定かな中なら反対のかな種別へ変換・確定 | TAB5向けに実装済み。オーバーレイに用途を表示する。 |
| `l`、`/` | 特別な英字・略語モードを持たない | 日本語入力中にコマンド名、パス、URL、識別子を入力する手段が弱い。 |

## 一般的なSKKとの照合

SKKは、かな漢字変換の対象となる見出し語を先頭大文字で明示し、送り仮名開始も大文字で指定する。候補の確定には`Ctrl+J`を使うことが基本で、Enterとは区別される。[1] そのため、シリアル端末では**`Ctrl+J`はIME確定専用として消費し、リモートにLF/CRを送らない**ことが重要である。

DDSKKには、`q`によるひらがな／カタカナのトグル変換、`/`で入る略語モード、数値変換、見出し語補完、単漢字変換、ユーザー辞書、学習などの拡張が存在する。[2] [3] これらを全て同時に移植する必要はないが、TAB5はリモート端末を操作する用途であるため、特にASCII入力への即時復帰とユーザー辞書は価値が高い。

## 記号・句読点の設計提案

### 1. P0：未対応特殊キーの安全な扱い

IMEが未確定または候補表示中の状態でTab、Delete、Up/Down、Home/End、Page、Insert、ファンクションキーが来た場合の方針を明文化する必要がある。推奨は、次の表のとおりである。

| キー群 | 推奨動作 | 理由 |
|:---|:---|:---|
| Enter、`Ctrl+J` | IME確定 | Enterは既存仕様どおりCR付き、`Ctrl+J`はCRなし。 |
| Escape | IME取消 | 既存仕様と整合する。 |
| Backspace、Left、Right | IME編集・候補操作 | 既存仕様を維持する。 |
| Tab | **未確定を保持したままリモートへ送らない**。初期版はIMEが消費して「Directへ切替してから再試行」のガイドを表示。 | リモートの補完とローカルの未確定文字列が競合することを防ぐ。将来は見出し語補完に利用できる。 |
| Delete、Up/Down、Home/End、Page、Insert、Fキー | 初期版は未確定を取消してからリモートへ送信する、または明示的にIMEを消費する。どちらか一方へ固定する。 | 状態乖離を避ける。端末操作を重視するなら「取消して送信」が実用的。 |

### 2. P1：句読点スタイルを設定化

現在の`.`→`。`、`,`→`、`、`-`→`ー`は自然な日本語文向けだが、シリアル端末ではASCIIの`.`、`,`、`-`が多用される。以下の設定を追加することを推奨する。

| 設定案 | `.` | `,` | `-` | 想定用途 |
|:---|:---:|:---:|:---:|:---|
| 日本語（既定候補） | `。` | `、` | `ー` | 日本語の会話・文章 |
| 全角欧文 | `．` | `，` | `－` | 技術文書、和文中の欧文 |
| ASCII優先 | `.` | `,` | `-` | シリアルコマンド、パス、設定値 |

この設定は**IMEの挙動だけ**を変え、Directモードの既存送信は変更しない。記号が混ざる未確定かなに対してSpaceを押した場合は、辞書検索の対象とせず、かな部分を確定してから記号を送る規則も必要である。

### 3. P1：`z`プレフィックスの最小セット

SKK系の実装では、`z`を記号入力のプレフィックスとして使う慣習がある。少なくとも`z/`の中黒、`z-`の波ダッシュ、`z.`の三点リーダを備えると、日本語文の入力効率が大きく向上する。[4]

| 推奨入力 | 出力 | 優先度 | 備考 |
|:---|:---|:---:|:---|
| `z/` | `・` | P1 | 中黒。カタカナ複合語に頻出。 |
| `z-` | `〜` | P1 | 波ダッシュ。Unicode正規化上の扱いをREADMEで明記する。 |
| `z.` | `…` | P1 | 三点リーダ。 |
| `z,` | `‥` | P2 | 二点リーダ。 |
| `z[` / `z]` | `『` / `』` | P2 | 和文引用符。 |
| `z{` / `z}` | `【` / `】` | P2 | 見出し・注記。 |
| `z!` / `z?` | `！` / `？` | P2 | 全角感嘆符・疑問符。 |

`z`は現実装では`za`などのローマ字入力にも使われるため、実装時は**未確定かなの途中で無条件に捕捉しない**ことが必須である。`z`の後に対応記号が来た場合だけ置換し、それ以外は通常のローマ字変換へ戻す有限状態機械にする。

### 4. P1：英字・記号を確実に入力する経路

現行は`Ctrl+Alt+J`でJapaneseモードを切り替えられるため、ASCIIを確実に送る逃げ道はある。しかし端末作業中に頻繁にモードを切り替えるのは負担である。

| 候補 | 提案 | 評価 |
|:---|:---|:---|
| 簡易ASCII一時入力 | `l`でASCII直入力、次の確定またはEscapeでJapaneseへ戻る | SKKらしいが、現行ローマ字表の`l`小書きかなと競合する。キー変更または明確な状態条件が必要。 |
| 略語モード | `/`でASCII見出し語を入力し、Spaceで辞書検索またはEnterで確定 | URL、コマンド、識別子、英単語に有用。DDSKKにも略語モードがある。[2] |
| 既存ショートカット | `Ctrl+Alt+J`でJapaneseを完全ON/OFF | 今すぐ使えるが、短いコマンドには操作数が多い。 |

最初の実装としては、**`Ctrl+Alt+J`を維持しつつ、`/`による略語モードをP1**とする。`l`は小書きかなとの互換性を検討してから採用する。

### SDカード経由のユーザー辞書インポート／エクスポート

Tab5にはmicroSDカードスロットがあり、ESP-IDF向けBSPでもSDカード機能が提供されている。SDカードはFAT32を前提とし、ユーザー辞書の交換ファイルはUTF-8/LFのSKK形式`/TAB5-SKK/SKKUSER.TXT`とする。[5] エクスポートは、SPIFFS上のユーザー辞書を8.3形式の一時・バックアップ名で安全に公開する。FATFSの既存ファイル上書き制約に対応し、既存ファイルを退避してから新しいファイルを公開する。インポートは構文と1行あたりの最大長を検証し、初期値を**マージ**にする。置換は既存の学習内容を失うため、画面上でファイル名と件数を確認した後にだけ実行可能にする。

この機能は実装済みである。SDカードの未挿入またはFATマウント失敗、ファイル不在、読み書きエラー、形式不正はDictionary Editorの状態欄へ明確に表示する。

## 今回は見送るべき事項

連文節変換、外部辞書サーバ、Lisp評価、複雑な文脈学習は、TAB5のスタンドアロン・シリアル端末という用途に対しては優先度が低い。特に連文節変換はSKKの基本設計から外れ、メモリ・UI・辞書管理を大きく複雑化する。[1]

また、標準SKKの「ローマ字ごとの即時かな確定」をそのまま再現することは、現在のTAB5オーバーレイ方式と相性が良くない。TAB5版は「未確定かなをローカル表示し、Spaceで候補検索」という一般IME寄りの操作を既に採用しているため、既存ユーザーの操作を壊さないことを優先すべきである。
